# MoveNest AI Process

## 1. AI 在项目中的角色

本项目将生成式 AI 作为产品分析、文案探索和前端实现的协作工具，而不是产品决策或健康判断的最终负责人。

AI 主要参与：

- 拆解产品目标和原型边界。
- 探索核心用户链路与页面信息层级。
- 生成英文 UI 文案候选。
- 提供 React、Vite、Tailwind 的实现建议。
- 协助检查范围、交互一致性和文档完整性。

人工负责：

- 确定目标用户、产品取舍和优先级。
- 判断哪些输出符合场景，哪些需要删除。
- 审核健康、安全和隐私风险。
- 校正文档与实际原型能力是否一致。
- 运行构建、Lint 和交互验证。

## 3. 从产品问题到原型的过程

### 阶段一：明确问题

先将宽泛的“AI x 运动健康产品”收敛到一个具体任务：帮助忙碌、缺少稳定运动习惯的用户完成第一次短时居家训练。

AI 用于提出用户链路和功能候选，人工删除了真实登录、社区、会员、完整课程库等会分散核心叙事的内容。

### 阶段二：定义体验

形成五页核心链路：

`Welcome -> Home -> Workout Detail -> Active Workout -> Completion`

人工保留了以下关键体验：

- 游客开始。
- 默认推荐。
- 训练前状态 Check-in。
- 课程安全与低冲击解释。
- 训练中 Pause、Skip 和 Too hard。
- 完成后难度反馈。

### 阶段三：生成文案与视觉方向

AI 提供英文文案和页面结构候选。人工删除了减脂羞辱、意志力施压和过度承诺类表达，保留更克制的 wellness 语气。

视觉上采用暖色背景、柔和橙色强调、圆角移动端界面和较强的留白。最终视觉不是由 Prompt 自动决定，而是经过前端实现中的持续人工调整。

### 阶段四：前端实现

AI 辅助形成单页 React 状态流、静态课程数据和组件结构。当前实现使用 `screen` 状态切换页面，没有引入 Router 或后端。

人工重点核对：

- 所有核心按钮是否能走通。
- 计时、暂停、跳过和反馈状态是否可演示。
- 文档是否如实描述实际能力。
- 构建和 Lint 是否通过。

## 4. 代表性 Prompt

### Prompt 1：拆解产品链路

```text
你是一名 AI x 运动健康产品经理。请为“面向欧美城市女性用户的居家训练 App”拆出一个 5 页面移动端 Demo 的核心用户链路。

目标用户是 25-35 岁、工作忙、没有固定健身习惯、希望在家做低压力短时训练的欧洲城市女性。请说明每个页面的目标、用户心理、核心信息和主按钮，不扩展登录、社区、会员等非核心功能。
```

人工判断：

- 保留五页闭环。
- 将首次开始训练作为唯一主任务。
- 删除会增加实现成本但不能增强核心论点的功能。

### Prompt 2：生成英文产品文案

```text
请为名为 MoveNest 的 gentle home workout app 写英文 UI 文案。品牌定位是 calm, clean, premium, European wellness。

不要使用减肥羞辱、焦虑驱动或强刺激健身房风格文案。页面包括 Welcome、Home、Workout Detail、Active Workout 和 Completion。文案应自然、简洁，适合首次打开 App 的用户。
```

人工判断：

- 删除 `burn fat fast`、`transform your body`、`no excuses` 等表达。
- 保留 `Start small`、`You showed up` 等强调行动和完成感的表达。
- 避免“AI 一定懂你”之类无法证明的承诺。

### Prompt 3：生成实现方案

```text
请用 React + Vite + Tailwind CSS 设计一个无后端移动端 Web App 原型。

不使用 Router，用 React state 控制页面切换。页面包括 Welcome、Home、Workout Detail、Active Workout、Completion。静态数据集中管理，按钮包含 hover、active 和 focus 状态，整体居中模拟手机端。
```

人工判断：

- 采用单页状态切换以控制 Demo 复杂度。
- 保留可点击核心流程。
- 使用本地图片资源，避免运行时依赖外部图片服务。

### Prompt 4：检查范围

```text
请从产品完整性、用户价值和实现可行性角度审查 Demo 范围：是否能体现个性化推荐和训练反馈闭环？是否有不必要的功能？是否能在 1 分钟内走通核心路径？

请指出应该删除、保留和强化的部分，优先保证 Demo 清晰、可信、可讲述。
```

人工判断：

- 保留“推荐 -> 开始 -> 调整 -> 完成 -> 反馈”。
- 将“60 秒内开始”定义为待测试假设，而不是已达成结论。
- 明确当前个性化只是规则与文案模拟。

## 5. 被拒绝或收敛的方向

| AI 建议或常见扩展 | 处理方式 | 原因 |
| --- | --- | --- |
| 完整登录和账号体系 | 删除 | 与首次训练主任务关系弱 |
| 大型课程库和筛选器 | 删除 | 增加选择压力，也扩大实现范围 |
| 社区挑战和排行榜 | 删除 | 不属于本次核心假设 |
| 真实 AI API | 暂缓 | 缺少数据、评估和安全机制 |
| 跳跃、波比跳等高冲击动作 | 删除 | 与新手、低压力和公寓场景不一致 |
| 医学化推荐或恢复承诺 | 删除 | 超出产品能力和安全边界 |

## 6. 如何判断 AI 输出是否可信

### 场景一致性

输出必须服务“快速开始第一节低压力训练”。如果建议引入复杂问卷、商城或社交功能，则判断为偏离核心任务。

### 实现一致性

文档不能把文案变化写成真实模型推荐，也不能把一次点击写成已经持久化的计划。所有能力描述需与代码行为交叉核对。

### 文案自然度

英文文案需避免直译感、夸张承诺和羞辱性表达。必要时通过母语使用者或目标市场用户进一步校对。

### 健康安全

AI 生成的动作和提示不能直接视为专业训练建议。正式产品需要专业人员审核、风险筛查、停止运动提示和保守降级策略。

### 技术验证

AI 生成代码必须经过：

- 人工代码检查。
- `npm run build`。
- `npm run lint`。
- 核心流程手动点击验证。

## 7. 当前原型中的 AI 能力边界

当前 Demo 不调用模型：

- Check-in 只改变解释性文案，不改变默认推荐课程。
- Too hard 只显示提示，不会真实调整动作。
- 完成反馈不持久化，也不会形成下一次模型输入。

这部分设计的目标是展示未来产品交互，而不是证明推荐算法已经完成。

若进入 MVP，应优先建立：

1. 明确的安全规则与禁忌过滤。
2. 可解释的候选排序。
3. 对错误推荐和高风险输入的降级处理。
4. 离线评估集和真实用户测试。
5. 健康数据的同意、删除和用途控制。

## 8. 素材与版权说明

原型图片均作为本地静态资源存放在 `src/assets`，运行时不请求外部图片服务。

项目尚未完整记录这些图片的原始生成工具、Prompt、授权来源或版权信息，因此目前不能确认其商业使用范围。对外公开或上线前，应补齐每张素材的来源和授权；无法确认时，应替换为自有、明确授权或可商用素材。

## 9. 复盘

AI 在本项目中最有效的作用是快速扩大方案空间和降低实现成本；最需要人工介入的部分是范围收敛、健康安全、文案可信度和能力边界。

本次最重要的修正是把“AI 个性化已实现”改为“用规则和状态模拟个性化体验”。这使文档与原型保持一致，也为后续真实推荐系统留下可验证的建设路径。
